# Self-Hosted Processing Runner

`HVO.SkyMonitor.ProcessingRunner` is the `processing-runner-v1` runner: a
self-contained linux-x64/linux-arm64 process that registers with LogicHost,
claims runner-placed central recipe jobs, fetches inputs under each job lease,
executes the shared recipe kernel, and uploads products. The contract is
documented in `docs/contracts/processing-runner-v1.md`.

## LogicHost configuration

Runners are off by default. Enable them and place recipes in the
`ProcessingRunners` section:

```json
{
  "ProcessingRunners": {
    "Enabled": true,
    "Placement": { "encoded-preview": "Runner", "image-quality": "Runner" },
    "Requirements": { "image-quality": { "ResourceClass": "standard", "LatencyClass": "background" } },
    "HeartbeatInterval": "00:00:30",
    "StaleAfter": "00:01:30",
    "LeaseDuration": "00:02:00",
    "RenewalInterval": "00:00:30",
    "ClaimBackoff": "00:00:02",
    "BacklogDegradedAfter": "00:10:00"
  }
}
```

Only built-in recipe names are accepted; transient runtime recipes cannot be
placed. A placed recipe is skipped by the in-process worker, so placing a
recipe with no active runner creates backlog (health check
`processing-runners` reports `Degraded`). Add a confidential client for runners
with scopes `api.runner api.artifacts.read` (for example
`DatabaseSeed:ConfidentialClients:N` with client id `system-processing-runner`).

## Runner configuration (environment)

| Variable | Meaning |
| --- | --- |
| `HVO_RUNNER_LOGICHOST_URL` | LogicHost base URL; https unless loopback or `HVO_RUNNER_ALLOW_INSECURE_HTTP=true` |
| `HVO_RUNNER_CLIENT_ID`, `HVO_RUNNER_CLIENT_SECRET` or `HVO_RUNNER_CLIENT_SECRET_FILE` | Runner OAuth client credentials |
| `HVO_RUNNER_ID` | Stable runner id (default `<host>-<arch>`); bound to the client subject on first registration |
| `HVO_RUNNER_DISPLAY_NAME` | Operator label |
| `HVO_RUNNER_MAX_CONCURRENCY` | Claim/execute slots (1-32, default 1) |
| `HVO_RUNNER_RESOURCE_CLASS`, `HVO_RUNNER_LATENCY_CLASS`, `HVO_RUNNER_LABELS`, `HVO_RUNNER_GPU_AVAILABLE` | Matching labels (lower-case labels, comma-separated list) |
| `HVO_RUNNER_MAX_TRANSFER_BYTES` | Per-claim/completion transfer limit (default 100 MiB) |
| `HVO_RUNNER_IDLE_SHUTDOWN_SECONDS` | Exit after this idle period (0 = never) |
| `HVO_RUNNER_SHUTDOWN_GRACE_SECONDS` | Drain time for active jobs on SIGTERM (default 30) |
| `HVO_RUNNER_REQUEST_TIMEOUT_SECONDS` | HTTP timeout (default 300) |

Arguments: `--capabilities`/`--self-test` warm up and print the capability
document (exit 1 when warm-up fails); `--probe` is the container health check
and never heartbeats: it requires the liveness file the runner loop rewrites on
every successful heartbeat (`HVO_RUNNER_LIVENESS_FILE`, default
`/tmp/hvo-processing-runner.alive`) to be younger than
the larger of `HVO_RUNNER_PROBE_MAX_AGE_SECONDS` (default 90) and three
negotiated heartbeat intervals (the file records the interval and is written at
registration, before the first heartbeat), and LogicHost's non-mutating
status to report `Active`, so a hung runner loop fails the probe instead of
being revived by it. On SIGTERM the runner stops claiming, keeps heartbeating
and renewing while in-flight jobs finish within `HVO_RUNNER_SHUTDOWN_GRACE_SECONDS`,
then cancels what remains and retires. Logs are JSON lines on stdout/stderr
(`event` values such as `registered`, `eligibility-changed`, `job-completed`,
`job-failed`, `lease-lost`, `draining`, `idle-shutdown`, `retired`).

## Container

```bash
docker build -f src/HVO.SkyMonitor.ProcessingRunner/Dockerfile -t hvo-processing-runner:<revision> .
docker buildx build --platform linux/arm64 -f src/HVO.SkyMonitor.ProcessingRunner/Dockerfile -t hvo-processing-runner:<revision>-arm64 .
HVO_SKYMONITOR_REVISION=<revision> HVO_RUNNER_LOGICHOST_URL=https://logichost.lan \
  HVO_RUNNER_CLIENT_SECRET_PATH=/etc/hvo/runner-secret \
  docker compose -f deploy/split-host/compose.processing-runner.yml up -d
```

The example compose file runs read-only with all capabilities dropped, a tmpfs
`/tmp`, a pid limit, and CPU/memory limits; the runner needs outbound HTTPS to
LogicHost only. It is not generated by the installer (`Deployment.Cli`).

## Operations

- Registration state: `CentralProcessingRunners` (status `Active`/`Stale`/
  `Retired`, warm state, eligible recipes, heartbeat). Health check
  `processing-runners` exposes active/stale/retired counts and placed backlog.
- Meter `HVO.SkyMonitor.LogicHost.ProcessingRunner` and log events 2200-2212
  are pinned in `docs/validation/central-runner-runtime-signals.json`.
- A runner that advertises a different recipe implementation version is
  registered but never eligible for that recipe (`eligibleRecipes` in the
  registration response and log event 2200 show the resolved set).
- Lease loss (409/410 on renewal) stops execution; LogicHost expires or
  cancels the job through the existing worker maintenance. Restarting a runner
  re-registers under the same id (generation + 1).
- To stop using runners, set the recipe back to `InProcess` (or disable the
  section); pending runner-placed jobs become claimable in process immediately.
