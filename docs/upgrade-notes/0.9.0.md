0.9.0 is the first release, so there is no earlier release to upgrade from.

A host running a development build or an integration pre-release (`0.9.0-dev.<n>`) moves to it as follows:

- Read the Changed, Removed and Deprecated sections of the CHANGELOG first. The installer is `hvo-sky-install`, its
  exit codes follow the install contract (a refusal exits `3`, not `1`), and the signed-release options are gone:
  install from a release folder with `--release`.
- An instance installed by `hvo-skymonitor`, before the rename to the `hvo-sky` locations (`/etc/hvo-sky`,
  `/var/lib/hvo-sky`), has no alias or migration. Reinstall it with 0.9.0's installer.
- Upgrade any other instance with the release's own installer:
  `hvo-sky-install cameraagent upgrade --instance-id <uuid> --release <folder>`. An instance installed from an
  `--image-ref` has no release record, so this first upgrade says its installed version is not recorded.
- An upgrade now refuses a host whose Docker cannot enforce CameraAgent's memory, CPU and PID limits, and there is no
  override. On a Raspberry Pi, append `cgroup_enable=memory` to the single line of `/boot/firmware/cmdline.txt` and
  reboot before upgrading. `--plan` reports every such finding and changes nothing.
- Scripts that pass `--config FILE` should move to `--answers FILE` (the same members, plus `"schemaVersion": 1`,
  without `dryRun`, `resume` and `json`), and should stop passing `--migration-backward-compatible`. Both are still
  accepted, with a warning. Scripts that read exit code `1` as a refusal must read `3`.
- To use `hvo-sky`, the new runtime client, create an owner API key in CameraAgent's web UI (**Account**,
  **API keys**) and run `hvo-sky login --url <instance URL>`, which asks for it without echo. It never takes a key on
  the command line.
