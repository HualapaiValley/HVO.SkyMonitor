0.9.1 upgrades 0.9.0 and earlier 0.9.1 integration pre-releases. Read the
[0.9.1 changelog](https://github.com/HualapaiValley/HVO.SkyMonitor/blob/v0.9.1/CHANGELOG.md) before scheduling the upgrade.

- Download the published 0.9.1 release files for the host architecture and verify
  their checksums and GitHub attestations as described in the
  [release runbook](https://github.com/HualapaiValley/HVO.SkyMonitor/blob/v0.9.1/docs/runbooks/releases.md#checking-a-release). Use the installer
  from that verified release folder to inspect the upgrade first:
  `./hvo-sky-install-linux-arm64 cameraagent upgrade --instance-id <uuid> --release <folder> --plan`
  (use `hvo-sky-install-linux-x64` on x64). Review the plan and retain an independent
  backup of the instance's data, configuration, identity/key material and catalog
  selection before running the same command without `--plan`.
- The approved checkpoint-recovery contract is not a claim that complete instance
  recovery is qualified in this release. The installer still uses the legacy
  image-swap/store-copy mechanism; bulk capture data is not copied. Do not assume
  that swapping back to an older image restores all candidate-mutated state. Read
  the [installer lifecycle limits](https://github.com/HualapaiValley/HVO.SkyMonitor/blob/v0.9.1/docs/runbooks/deployment-installer.md#cameraagent-lifecycle)
  and the [qualification and adoption gates](https://github.com/HualapaiValley/HVO.SkyMonitor/blob/v0.9.1/docs/hvo-install-contract.md#skymonitor-qualification-and-adoption)
  before choosing a recovery procedure. Do not attempt a manual binary downgrade
  against state changed by a newer version.
- Release installs and upgrades now place verified `hvo-sky` and `hvo-sky-install`
  commands on PATH and retain replaced programs as `.previous`. Review the plan's
  command paths and ownership checks, especially on hosts sharing commands between
  instances. Use the durable installer's reported path for resume and recovery;
  see [installed commands](https://github.com/HualapaiValley/HVO.SkyMonitor/blob/v0.9.1/docs/runbooks/deployment-installer.md).
- For a 0.9.0 host, the legacy scene-overlay producer changes from v10 to v13,
  the cloud producer from v4 to v5, and the environment producer from v5 to v6.
  Customized cloud/environment-only graphs are affected even without a scene-overlay node.
  Early 0.9.1-dev.1 through dev.5 scene producers v11/v12 also move to v13.
  A Named active revision with superseded node plans cannot run live processing:
  `capture-processing` health becomes Degraded with
  `active-revision-superseded`, and standard processing is abandoned. Raw capture
  and upload continue. On Named graphs (`/operations/pipeline/graphs`), create a
  new revision from the pipeline definition, validate it with the installed
  version, then explicitly activate it; alternatively select configured-basic.
  Revalidating an already Validated revision cannot replace its immutable plans.
  Previously accepted replays with obsolete plans expire on claim with
  `processing.plan-superseded`; submit a fresh replay against a compatible
  revision to process the retained raw evidence. Activation cannot repair a
  replay's frozen plan. Retained products keep their recorded rendering.
- New graph-editor settings require a draft, validation and explicit activation;
  they do not rewrite archived images. The installed legacy scene alias uses
  v13. Use the reviewed whole-draft
  [scene-style upgrade](https://github.com/HualapaiValley/HVO.SkyMonitor/blob/v0.9.1/docs/runbooks/scene-style-options.md) to adopt the explicit
  v14 style producer. Do not edit version fields by hand. Expected-position star
  names are qualified as expected; measured astrometry, measured associations
  and satellite capture predictions require explicitly enabled processing and
  suitable retained inputs. They do not change rig calibration automatically.
- Orbital-element, space-weather and time-data refresh are opt-in. Review the
  [orbital refresh](https://github.com/HualapaiValley/HVO.SkyMonitor/blob/v0.9.1/docs/runbooks/orbital-elements-refresh.md) and
  [space-weather refresh](https://github.com/HualapaiValley/HVO.SkyMonitor/blob/v0.9.1/docs/runbooks/space-weather-refresh.md) runbooks before
  enabling their reserved automations. Provider floors and halts in those stores
  survive installer rollback. Creating any of the three new reserved automation
  kinds leaves definitions, revisions or runs that 0.9.0 cannot parse: its
  automation store fails closed and all local automations stop. Removing the
  definition alone does not make returning to 0.9.0 safe. Prefer upgrading
  forward; do not manually downgrade against this state.
- If return to an older build is unavoidable and otherwise admitted by the
  installer, follow the documented
  [automation archive and disposition procedure](https://github.com/HualapaiValley/HVO.SkyMonitor/blob/v0.9.1/docs/runbooks/orbital-elements-refresh.md#rollback):
  stop CameraAgent; archive the entire `<RawIngressRoot>/.automation/` directory,
  including `-wal`/`-shm` sidecars, to owner-controlled storage; record its checksum
  and disposition; move that directory aside before starting the older build.
  The older build creates an empty automation store, so definitions must be
  restored or recreated deliberately. Leave `.orbital-elements/`,
  `.space-weather/` and `.time-data/` intact. On roll-forward choose the archived
  automation store or the replacement explicitly; never merge them by editing
  rows or erase provider floors/halts. This procedure is not a complete instance
  checkpoint and does not bypass schema or recovery admission checks.
- Satellite planning now has bundled verified Earth-orientation and leap-second
  data. Configured file overrides still take precedence; an incomplete or invalid
  override stops planning. For coverage and expiry, open Observatory & location
  -> Orbital refresh & satellite setup -> Read-only time-data configuration and
  resolved status (`/operations/site#satellite-time-data`), or run
  `hvo-sky time-data`. For optional managed updates, first turn on Time-data refresh
  there (or `hvo-sky config set timeDataRefresh.enabled=true`), then create the
  reserved automation using Automations -> Time-data refresh setup
  (`/operations/automations?setup=time-data`). It uses identifier
  `time-data-refresh`, task `TimeDataRefresh`, target `iers-usno`, and interval
  86,400 seconds. See [Satellite Planning Time Data](https://github.com/HualapaiValley/HVO.SkyMonitor/blob/v0.9.1/docs/runbooks/orbital-elements-refresh.md#satellite-planning-time-data).
  Unavailable data never means an empty sky.
- Current Sky retains layer choices and waits for completed processing before
  advancing at `currentSky.minimumRefreshSeconds` (default 15 seconds). Review
  that setting if an operator expects every acquired frame to appear immediately.
- Package pins include .NET 10.0.14, but the runtime images and SDK-bundled runtimes
  remain at 10.0.13. This release does not claim the separately tracked runtime
  upgrades. Release CameraAgent images use the per-architecture ReadyToRun trial;
  native publish repeatability and platform performance remain release evidence,
  not conclusions established by these notes.

For installations predating 0.9.0, also follow the
[0.9.0 upgrade notes](https://github.com/HualapaiValley/HVO.SkyMonitor/blob/v0.9.1/docs/upgrade-notes/0.9.0.md), including the legacy installation-name migration
and host container-limit requirements.
