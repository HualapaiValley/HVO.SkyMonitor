# Diagnostic output boundaries

Errors and warnings follow one of these routes. Redaction always precedes escaping.

* Raw exceptions from every CLI source go through `Program.WriteErrorAsync` and
  `CameraAgentStateDiagnostics.Message`. It redacts the whole first line before
  the existing 256-character limit, then escapes remaining controls. Printable
  punctuation keeps the existing human output; JSON receives its usual envelope.
* The privileged internal commands bypass the top-level catch. Their six catch
  sites and the wizard startup catch use `Message` directly. Usage errors and
  parse advisories use the same boundary. Usage/help text is generated by the
  installer, rather than copied from an exception's untrusted input.
* `HostPrerequisites` and `CameraAgentStatePreflight` render multi-line reports,
  so `Text` formats each complete untrusted field without truncating its remedy.
  Their JSON output uses `ForOutput`, a sanitized copy; persisted evidence is
  unchanged. Host advisory and recovery-limit warnings format their fields too.
* Backup, restore, snapshot, archive, inventory, restored-credential and vault
  sources compose fixed prose from `Reason`, `Field`, `Assignment`, `Identity`
  and `Failure`. Only these sources may set `IsFormattedDiagnostic`. The writer
  preserves that marker so a hostile field cannot cause a second scan to hide
  the remedy or the phrase “password and security stamp”. New marked sources
  must first join `Diagnostic1476_AllOwnedFailureMessagesAreSafe`.
* Lifecycle progress and upgrade-release notes are structured progress/content,
  rather than diagnostic exception text; their existing typed renderers own them.

`Diagnostic1499_OutputAndMarkerBoundariesAreClosed` enumerates every CLI source,
checks direct error writers and closes the formatted-owner list. The hostile
interpolation sweep covers the composed sources; real SQLite and top-level tests
exercise human and JSON paths. New direct writers must be classified and tested.

Space-only compound keys use identifier segments beginning with a letter,
separated by `_` or `-` (for example `db_password` and `x-api-key`). This keeps
credential values containing numeric prose segments from becoming nested keys.
Explicit `=`/`:` keys retain the existing suffix-based matching.

A secret key's words may be joined by `-`, `_` or nothing (`SecretKey`,
`secret-access-key`, `ObjectStorage__SecretKey`); `secretkeeper` stays ordinary.
A quoted value may follow its key after `=`, `:` or any whitespace, including a
tab or a no-break space, and is hidden whole. After a space-only key it keeps its
quotes (`db_password "<redacted>"`) unless text is joined to the closing quote,
which is hidden with the value.

Nested matching accepts the temporary removed-decoration boundary before or inside
an inner credential key. The boundary is removed only after the value is hidden.
